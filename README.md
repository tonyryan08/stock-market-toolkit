# Intro to the Stock Market — course toolkit

A community-school course in good financial decision-making, and the Cloudflare Workers toolkit that powers it — built in public, one capability per week, over twelve weeks.

**We grade decisions, not outcomes.** Paper portfolios only. No tips, ever. **Education, not advice** — nothing in this repository is a recommendation to buy or sell anything.

## Quickstart

Prerequisites: Node 20+. Five secrets (see `.dev.vars.example` and `docs/api-keys-guide.md`): two free data keys, a Claude API key (pre-paid, for the explain route — the site works without it), an EDGAR User-Agent (not a key: the project name and an email, which the SEC's fair-access policy requires), and from week 12 the tutor's email address(es) for the door.

```sh
npm ci             # a fresh clone: installs exactly the lockfile (npm install under another npm rewrites it — Phase 3 review N16); `npm install` after a shipment that changes a pin
npm test           # 628 tests
npm run check      # wrangler types + tsc
npm run dev        # http://127.0.0.1:8787 (wrangler binds the IPv4 loopback; `localhost` can resolve to ::1 on Windows and not answer)
```

First-time data setup, in this order (the detail is in `docs/setup-guide.md`):

```sh
npm run verify-universe                                   # probe the candidates (~2 FMP calls each) → scripts/seed-universe.sql
npx wrangler d1 create stock-market-db                    # paste the database_id it prints into wrangler.jsonc
npx wrangler d1 migrations apply stock-market-db --local  # 0001 … 0014
npx wrangler d1 execute stock-market-db --local --file=scripts/seed-universe.sql
npm run seed-small-caps                                   # EDGAR lookups only → scripts/seed-small-caps.sql
npx wrangler d1 execute stock-market-db --local --file=scripts/seed-small-caps.sql
npm run dev:cron                                          # then ring the doorbell (Runbook → "The doorbell")
```

## Deploy

```sh
npx wrangler login
npx wrangler d1 migrations apply stock-market-db --remote
npx wrangler d1 execute stock-market-db --remote --file=scripts/seed-universe.sql
npx wrangler d1 execute stock-market-db --remote --file=scripts/seed-small-caps.sql
npm run deploy
```

Production fills itself: the first 22:30 UTC run backfills the core tier (stalest first, 45 fetches per invocation, the rest the next night — two landlord's meters taught us that, see the record), accounts arrive at 15 companies a night, and the small-cap tier fills at ~5 companies per `npm run smallcaps`. Releasing is `npm run deploy`; GitHub Desktop commit + push is the backup habit. Deploy-on-merge CI exists but is **parked by decision #6** (`.github/workflows/deploy.yml`, manual trigger only).

## Runbook

The things a successor needs that the weekly lessons do not say. Everything below is also in the shipment notes that built it, but those are not in the repo (decision #16).

**Secrets — five, never in files.** Live: `npx wrangler secret put NAME` for `ALPHAVANTAGE_API_KEY`, `FMP_API_KEY`, `ANTHROPIC_API_KEY`, `EDGAR_USER_AGENT` and, from week 12, `TUTOR_EMAILS` (the tutor's address or addresses, comma-separated — an email is personal data, so a secret, never a `vars` entry in this public repository); `npx wrangler secret list` shows the five names. Local: the same five in `.dev.vars` (gitignored), plus `SMALLCAP_AV_CALLS="4"` so a local small-cap run spends 4 Alpha Vantage calls, not 20 — the key is shared with production. Stage a value for `secret put` in a text file **outside** the project folder (`type C:\Users\you\Desktop\key.txt | npx wrangler secret put NAME` on Windows), never inside it: K-2 in the record is what happens otherwise, and `.gitignore` now refuses `key*.txt` and `ua.txt` anyway. A key that has been on a screen is no longer a key: rotate it.

**Rations.** Alpha Vantage free: 25 calls in any rolling 24 hours, 5 a minute, metered by key *and* by sender address. The small-cap visit plans within the rolling ration it reads from its own receipts — visits and live quotes of the last 24 hours plus a ten-minute margin (a receipt is stamped at a run's start; its calls follow over the next minutes), three kept back — and `--calls N` (default 20) is only a ceiling (v0.10.0, OI-51); a receipt it cannot read leaves a `ration_error` line and the ceiling is planned, as before; the tutor's live quote demo (`/api/quote/:ticker`) is capped at 3 a day on the same key (`QUOTE_DAILY_CAP`; `"0"` switches it off), answering 429 with the cached close once spent. FMP free: 250 a day; the nightly job counts its own fetches (45 per invocation, Workers Free's limit is 50) and resumes next night. Claude: one generation per company per fact-sheet fingerprint, 60 a day (`EXPLAIN_DAILY_CAP`), cost in hundredths of a cent per story; the tutor, 60 questions a day (`TUTOR_DAILY_CAP`; `"0"` shows the passages only), about three thousand input tokens each (the prompt and six passages — 2,200–3,400 measured at VC-22) — nothing is called when no passage matches, and the budget is counted before the call (a `pending` row, so a burst cannot walk through it); the process review, 3 readings a day per student (`REVIEW_DAILY_CAP`) and 40 for the class (`REVIEW_GLOBAL_CAP`; `"0"` on either shows the audit only), counted the same way in `reviews` — a failed call that returned nothing is not counted, so an outage cannot spend a student's day — 1,400–1,600 input tokens each (measured at VC-23); the audit and the worksheet call nothing. D1: 100k metered writes a day — each insert counts the table plus every index, which is why `migrations/0002` dropped one and why no later migration adds any.

**The nightly alarms** (`wrangler.jsonc` → `triggers.crons`): `30 22 * * *` and `40 22 * * *` are price runs (any `mm 22` line is; add a line to add 45 fetches of capacity), `50 22 * * *` is the accounts run, and `0 23 * * *` the **signals** pass followed by the **stop tracker** and then the **risk report** (all three D1 only, no provider calls: one row per instrument in the `signals` table, then every open paper position's trailing stop, then one `risk_reports` row per student per night (keyed on the night's latest close, not on a lagging position's), the account marked to the latest closes, the high-water mark carried from the last row, the flags — its own invocation so a fault in one phase never costs another, each pass fenced on its own). There is no small-cap cron: `10 23 * * *` is still understood by the handler for the PC visit, but it is not scheduled. Edit the crons line in Notepad; `npm run deploy` prints the schedules it registered.

**The doorbell (local runs).** With `npm run dev:cron` running, open in the browser: `http://127.0.0.1:8787/__scheduled?cron=30+22+*+*+*` (prices), `…?cron=50+22+*+*+*` (accounts), `…?cron=0+23+*+*+*` (signals, stops and the risk report — free, no calls), `…?cron=10+23+*+*+*` (small caps), `…?cron=*+*+*+*+*` (everything). On wrangler builds where that path 404s, the same query on `/cdn-cgi/handler/scheduled` is the current one; the visit script tries both. A company visited in the last six hours is skipped, so ringing twice costs nothing — but a *local* ring spends the shared Alpha Vantage key.

**The small-cap visit from your PC** (v0.8.1, I-4). Once: save `wrangler.smallcaps.example.jsonc` as `_wrangler.smallcaps.jsonc`, paste the `database_id` from `wrangler.jsonc` over the zeros (the underscore keeps it out of git). Then `npm run smallcaps -- --calls 18` (an unknown or malformed argument stops it before it rings — OI-50): it starts the Worker locally on port 8790 with the **live** database bound remotely (wrangler ≥ 4.37's `"remote": true`), rings the doorbell, polls the live `fetch_log` for up to 14 minutes, prints the receipt and stops the server. Expect `ok` + `fund_ok` per company visited, `avCalls ≤ N`, and `blocked` where Alpha Vantage has no series. Dividends refresh every 100 days on their own (one call); accounts every 400 (three calls); EPS gaps retry EDGAR-only at no Alpha Vantage cost; a 403 from EDGAR is a User-Agent problem and is not retried. **Run it once a day** — while the tier fills (~10 runs), while it matures to 128 closes (the stored series grows only on a visit, and a small cap's rule reads from the close of its last visit), and after, because a small-cap ticket prices on that close too; weekly leaves the tier up to a week stale (OI-07, amended at week 11). **The ration is a rolling 24 hours, not a calendar day** (24 Oct: the 26th call since the previous evening was refused at 10:07 UTC; two runs in the following week were cut short by an early start). Since v0.10.0 the Worker counts the last 24 hours' calls from the receipts and plans within them, so the hour no longer matters: a run on a spent ration fetches nothing and the receipt says when the window frees. Never re-run a VC's preparation lines; a run stopped by the limit mid-visit puts that company first in the next run's queue.

**Enrolling students (weeks 8–9).** `npm run enrol -- --name "Ada Lovelace" --capital 10000` writes a row to the live `students` table through `wrangler d1 execute --remote` and prints the code once (`XXXX-XXXX`, no ambiguous characters); `npm run enrol -- --list` shows them again, with each account's instruments; `--local` does the same to the local database for a rehearsal. `--instruments N` (1–4, default 1) sets how many instruments the account runs — each position is sized at 12% ÷ N a year and the ticket refuses the (N + 1)th open position; `npm run enrol -- --set-instruments CODE N` changes it later (positions already open keep their size; the nightly report flags an account over the count or the budget). From week 12 the student's **email is their login** (`--email ada@example.com` at enrolment; `npm run enrol -- --set-email CODE EMAIL` links an account enrolled earlier; `--list` shows which still lack one; a duplicate is refused unless `--allow-shared-email`, for the tutor's own test accounts) — the same address goes on the Access policy. The code stays the account's name on every ticket and in the tutor's list, and the page's URL (`/tickets/<code>`) opens for that email and the tutor's only; it was the student's identity before week 12 and still is while Access is off. From v0.11.0 the code is nowhere in the page's text, so a screenshot does not carry it (OI-56); the enrolment list stays off the repo like any other personal record. A paper account is between $500 and $1,000,000; the calculator shows what a small one cannot do.

**The tutor's notes (week 10).** The tutor reads the `notes` table, not the files: after any edit to a lesson plan or a kit document, `npm run seed-notes` regenerates `scripts/seed-notes.sql` (the passages, then the FTS5 index rebuilt from them) and `npx wrangler d1 execute stock-market-db --remote --file=scripts/seed-notes.sql` applies it — local first with `--local`. Passage ids are positional within a file (`L8.9`), so an edit can move them; the `questions` table keeps the ids each answer cited and the page shows the passage text. If the live database refuses the virtual table (the FTS5 spike), apply `scripts/seed-notes-plain.sql` instead: the same rows, no index, and the tutor ranks them by a plain word match on its own — the page's retrieval line says which it used. What the class asked is at `/api/tutor/recent` (anonymous). Retire a test account: `npm run enrol -- --retire CODE` shows what would go, `--yes` deletes the student and their tickets, positions and reports (no undo).

**The process review (week 11).** `/tickets/<code>/review` shows the audit (no model) and the last reading; the button asks for a fresh one and lands back on the page with it (a refresh spends nothing). `GET /api/explain-my-portfolio/<code>` is the audit as JSON; `?ai=1` asks for a reading — a plain GET spends nothing, so a link preview or a prefetch cannot. The sheet the model reads is on the page under "The sheet the AI reads": process facts only — none of the toolkit's P&L, account-value or drawdown figures, no price level beyond the entry; the student's own journal words are on it as written. A reading that fails any check (a fact not on the sheet, a paragraph citing nothing, a number from nowhere, a tip, outcome language) is withheld and the page says why; the audit stands. Every reading is a `reviews` row with its prompt version (`REVIEW_PROMPT_VERSION` in `src/lib/review.ts`, `r4` — bump it on any change to the prompt, the schema or the sheet's wording, so an old reading says which prompt wrote it) and the facts of its own night (an old reading's tags open those). The audit's thresholds: a stop answered within five nightly closes (the week's routine, counted on the universe's nights from the `signals` table) is on time; the journal notes are word tests. **The worksheet (week 11).** `/costs` and `/api/costs` price a paper trade in euro from `TAX_RULES` and `BROKER` in `src/lib/costs.ts` — every rate with its date and a `basis` of "Bill" or "current"; every mark and sentence on the page is derived from the basis, so when the Finance Act is law, set `checkedOn` and the three `basis` fields to "current" and the page follows (the rules' own `note` texts — "as announced", "drafted in the Bill" — are hand-edited at the same time; OI-86 lists them); confirm the broker's schedule the week of the lesson.

**Reading the receipt.** Every provider call and every run is a row in `fetch_log`:
```sh
npx wrangler d1 execute stock-market-db --remote --command "SELECT run_at, symbol, outcome, substr(detail,1,160) AS d FROM fetch_log ORDER BY id DESC LIMIT 40"
```
Outcomes — prices: `ok` / `error` / `blocked` (the plan does not serve the symbol — permanent until reset) / `av_jump` (a >40% day in the adjusted series; for the small tier the signal pass quarantines the symbol until a `splits` row within four days of the date explains it — a split, or factor 1 with a note for news; an `av_jump` line is permanent, so the factor-1 row is the way out. The `splits` table is read by the stop tracker for **any tier**: a row for a core-tier name is the recovery path for a `split_unknown`, the quarantine is the small tier's only) / `realigned` / `dividends` (a dividends-only visit); accounts: `fund_ok` / `fund_partial` / `fund_error` / `fund_blocked` / `fund_eps_missing`, with `edgar_failed`, `edgar_ok` (a retry) and `edgar_mismatch` (EDGAR's net income more than 1% from Alpha Vantage's); run-level: `rate_limited`, `auth_failed`, `av_premium`, `fetch_budget`, `write_error`, `write_limited`, `write_budget`, `run_summary`; the explain route's `explain_ok` / `explain_capped` / `explain_rejected` / `explain_error`; the tutor's `tutor_ok` (with the tokens, the retrieval mode and any flags) / `tutor_declined` (the model: the passages do not answer it) / `tutor_off_corpus` (no passage matched — no call) / `tutor_rejected` (advice-shaped language — withheld, on the page and in the API; the audit copy is the `questions` row) / `tutor_capped` / `tutor_error` (a deployment with no key writes a `questions` row and no log line); the process review's `review_ok` (the tokens, the prompt version, the breaches and notes counted, any flags) / `review_rejected` (outcome or advice language — the reading withheld; the audit stands) / `review_capped` / `review_error` (the audit alone writes nothing); the quote demo's `quote_demo`; the small-cap visit's `run_summary` with `ration_error` (the receipts could not be read; the ceiling is planned) and `smallcaps_error` (the fenced visit failed as a whole); the signal pass's `signals_error` / `signals_skipped`; the stop tracker's `stop_hit` / `realigned` / `split_realigned` / `split_unknown` (a re-alignment the tracker cannot explain — not dividend-sized, not an N-for-1, 1-for-N or p-for-q ≤ 5 ratio: the position is left untouched until a `splits` row settles it) / `stops_skipped` / `stops_error`; the risk report's `risk_flag` (one line per flagged student: value, mark, drawdown, risk used, the flags) / `risk_error` / `risk_skipped` (no signal rows to mark to yet). A `wrangler d1 execute --remote` that answers 7403 or 10000 is the control plane, not your data (I-2): retry the identical command, wait a minute, dashboard console, re-login — in that order.

**Resets.** Make a company due again: `UPDATE tickers SET fundamentals_as_of=NULL, last_price_fetch=NULL WHERE symbol='ETD'`. Retry a company marked `fundamentals_status='blocked'` (it is skipped until you do): `UPDATE tickers SET fundamentals_status=NULL WHERE symbol='X'`. Refetch five years for the core tier: `last_full_fetch=NULL` (the realign rotation does four a night anyway). Local D1 is `.wrangler/state` — delete it to start clean, then migrations and seeds again.

**Migrations** are the curriculum: `0001` init · `0002` the write budget · `0003` fundamentals · `0004` the value pool (tangible book) · `0005` explanations · `0006` the small-cap tier · `0007` dividends cadence + readings · `0008` signals · `0009` students, tickets, positions, splits (week 8) · `0010` `students.instruments`, `risk_reports`, `signals.quarantined` (week 9) · `0011` `notes`, `questions` (week 10; the FTS5 index is the seed's, not the migration's) · `0012` `reviews` (week 11) · `0013` the student's email (week 12) · `0014` `plans` (v1.1, the planner). Apply with `wrangler d1 migrations apply`, local then remote, never by hand.

**The door (week 12, decision #23).** The whole site stands behind **Cloudflare Access**, switched on from the Worker's own Access tab (Workers & Pages → the Worker → Access → *Protect this Worker behind Access* → *All traffic* → a policy whose Include rule lists the enrolled emails and the tutor's → *Apply Access*; the email one-time code is a login method added in Zero Trust — since June 2026 a new organisation's default is Cloudflare's own identity provider). Access does the login and hands the Worker the identity on `ctx.access` — the Worker validates no token itself (`src/lib/access.ts` reads `getIdentity()`); the rule is that a student's page opens for the email on their row or for `TUTOR_EMAILS`, `/me` finds the account by the signed-in email, and with Access off (`ctx.access` absent — local dev without the `access.dev` block in `wrangler.jsonc`, or the Worker made public from the same tab) the code scheme of week 8 stands unchanged, so one build serves both states. Order of operations on the night: every row linked, every address on the policy, the secret set, *then* the switch. Nightly jobs are unaffected (Access gates requests, not the schedule). The steps with the screens named are `docs/setup-guide.md`, Part E; the live check is VC-24.

**The planner (v1.1, decision #24).** `/plan/<code>` is the tutor's workbook after the course: tonight's names ranked by the tests — the watchlist's bands (the gate, the near misses that are long, the rule's longs that fail both screens, longs without books), then defensive tests passed, enterprising tests passed, the forecast (the rule's trend strength, from the price series), the lower instrument risk; never a return — the top ones picked to fill the account's instrument count, each sized by the Starter System at 12% ÷ N through the same `sizing.ts` the ticket judge uses, **on the judge's facts**: the account's value tonight less the opening costs of the rows above, fitted in rank order to the ledger cash (a calm share sizes to the whole account, so a second cannot fit — the row says so), with the stop's gap and level (the course's close-read stop, not a broker's resting order) and the costs in dollars beside the broker's euro lines from `costs.ts` at a rate you type (never fetched). The journal is in two parts: the facts the planner writes and the thesis only you can — a row without one is not raised. *Recompute* keeps your ticks, *Repopulate* picks the top names again, *Save* keeps the picks as typed (one row per account, migration 0014 — a blank units cell re-sizes with the rule each night), *Raise the tickets* writes each ticked row, up to the account's room, through `handleTicket` and shows the refusals in the judge's words; a form posted from another site is refused; `/plan/<code>/plan.csv` is the plan for Excel. Behind the door it opens for `TUTOR_EMAILS` only (a student is answered 403 with the way to `/me`); with the door off the code is the key, as on every student page.

**The upgrade path.** The tutor's retrieval is SQLite full-text search (FTS5) in D1, with a plain word match as the fallback (decision #3; the design is #21). **Vectorize + Workers AI embeddings are the documented upgrade path, not the plan**: if FTS5 ever fails the room (synonyms, paraphrase — the week-10 habit "use the course's words" is the mitigation), the same `notes` rows go into a Vectorize index through Workers AI's embedding model and `searchNotes()` in `src/tutor.ts` swaps its query — nothing else in the Worker changes. A sentence-level support check on the tutor's and the review's citations (does the cited passage carry the sentence?) is the same upgrade path's second step, not the plan (OI-83). The course is complete at v1.0; the register stays open (the Bill's figures in December, OI-86, first).

**What it costs to run (week 12).** Free plans for everything but the AI, which is a pre-paid balance bounded by the three daily caps; the allowances, the receipts' usage and the headroom are in [`docs/free-tier-cost-review.md`](docs/free-tier-cost-review.md) — the two D1 daily limits (100,000 rows written, 5 million read; enforced since 1 Sep 2026) are the ones to watch, at ~5% and ~3% of their allowance a night.

## How this was built

This project doubles as a working demonstration of AI-assisted delivery: design decisions in Claude chat, implementation in Claude Code, Claude-powered product features from week 6, an independent review (a second model, a cold clone, findings before changes) before important weeks ship — with every step logged in [`BUILD-LOG.md`](BUILD-LOG.md) and everything verified by hand before it's trusted. The same standard the course asks of its students: process on the record, graded before the outcome is known. Nobody leaves their brain or autonomy at the door.

**The method, every week, in the same order** (compiled from the BUILD-LOG — each entry has these headings): *Designed* (the decision in chat, written into `docs/syllabus.md` with a number) → *Built* (in a sandbox, with tests; nothing committed by the machine) → *Verified, machine* (the suite, `tsc`, a local Worker on a fresh D1 with the real migrations and seeds) → *Reviewed* (a fresh model on a fresh clone with the shipment laid over it, a written report, findings before anything is changed; the tutor decides each) → *Built again* (the findings the tutor said yes to) → *Verified again* → *Verified, hand* (the tutor applies the shipment on his own machine, deploys, and the live check — the VC numbers in `docs/data-provider-checks.md` — closes the week on live evidence) → the commit, by the tutor, from GitHub Desktop. A shipment is a zip of changed files with notes that end "You are at: step N"; the notes never enter the repository; neither does any key, code, address or personal record.
